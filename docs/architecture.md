# SheetCore 设计说明

> 这份文档只讲**为什么这样设计**。要跑起来看 [README](../README.md)，
> 要看代码结构看下面的包划分。

---

## 一、它解决什么问题

电子表格（Excel / Google Sheets）背后有一个**计算内核**，与界面完全是两件事。
你输入 `=SUM(A1:A10)` 时真正发生的是：

```
公式文本 --词法/语法分析--> AST --建依赖图--> 拓扑序重算 --> 值
                            ↑                        │
                            └── 某个格子变了，只重算受影响的部分
```

SheetCore 做的就是这件事，不含任何 UI。它面向把表格计算能力**嵌进程序**的场景：
配置表、规则表、财务模型，以及需要在代码里安全求值用户公式的地方。

**核心承诺是可解释的增量重算**：改一个格子，只重算真正依赖它的那些，
并且能说出"重算了哪几个、按什么顺序"。

## 二、包划分

```
value/       单元格值、错误值、类型强制转换        纯
reference/   A1 记法、$ 绝对标记、跨表引用、区域    纯
formula/     词法分析、AST、递归下降语法分析        纯
graph/       依赖图、脏传播、拓扑排序、环检测       纯
functions/   38 个内置函数                        纯
engine/      把上面五个接起来，增量重算 + 轨迹      纯
render/      终端排版：显示列宽、表格对齐           纯
cmd/main/    CLI：解析参数、排版输出                 I/O
```

**除 `cmd/main` 外全部是纯逻辑**，因此 151 个测试全部离线运行、不需要网络也不需要子进程。
这不是洁癖：`engine/` 里任何一个 bug 都能用一条断言钉住，而不是靠跑一遍看看。

## 三、六个关键决定

### 1. 错误是值，不是异常

`#DIV/0!` 在电子表格里会像普通值一样在依赖图里传播、被 `ISERROR` 检测、参与排序。
所以它是 `Value::Error(CalcError)`，不是抛出的异常。

收益很直接：**一个格子的错误不会让整张表算不出来**。
`=A1+1` 在 A1 是 `#DIV/0!` 时结果是 `#DIV/0!`，而不是程序崩掉。

代价是每个运算符都要处理错误分支。这是值得的 —— 表格里写错一个格子是最常见的事，
它不该让整个文档失效。

### 2. 函数实参有三种形态，不是一种

| 形态 | 来源 | 聚合时 |
|---|---|---|
| `Scalar` | 公式里写死的字面量 | **强制转换**：`SUM("2")` → 2，`SUM("abc")` → `#VALUE!` |
| `Cell` | 引用求值的结果 | **忽略**文本与空值：A1 是 "abc" 时 `SUM(A1)` → 0 |
| `List(values, rows, cols)` | 区域展开 | **忽略**其中的文本与空值 |

前两者的差异是电子表格的真实规则，合并会导致 `SUM(A1)`（A1 为文本）错误地报
`#VALUE!` —— 这个 bug 被单元测试抓到过（见第五节）。

`List` 额外带**行列数**：没有形状就无法索引，`VLOOKUP` / `INDEX` 根本写不出来。
扁平数组区分不了"第 3 个"与"第 2 行第 1 列"。

### 3. 拓扑排序返回结构体，不返回 `Result`

检测到环时，`Err` 会丢掉"剩下那些能正常计算"的顺序，而上层恰恰需要它：
环里的格子给 `#CYCLE!`，其余照常算完。

用 `Result` 就得再排一次，既慢又容易写出不一致。所以：

```moonbit
pub(all) struct TopoResult {
  order : Array[String]    // 可以按此顺序计算的
  cycles : Array[String]   // 卡在环里的
}
```

### 4. 排序必须确定，否则"可复现"是空话

Kahn 算法每一步在就绪集合里取**字典序最小**的节点。
没有这条规则，同一张图的排序会依赖 Map 的遍历顺序，
"同一串操作得到同一条重算轨迹"这个承诺就不成立，测试也会变得不稳定。

`Trace` 里刻意**不含耗时** —— 耗时取决于机器与调度，放进来会让同一次操作
产生不同的轨迹。性能请用独立的基准衡量。

### 5. 求值只读缓存，不递归

`engine` 按拓扑序走一遍：轮到某个格子时，它的前置**已经算完并缓存**了。
所以求值过程不会回头调用别人，也就不可能出现"算到一半又绕回来"。

这既是增量的前提，也是环能被安全处理的保证 —— 环在排序阶段就被识别出来了。

### 6. 跟随电子表格那些反直觉的地方

声明的是"电子表格语义"，所以明知反直觉也跟：

| 行为 | 直觉 | 电子表格（本项目的选择） |
|---|---|---|
| `-2^2` | `-(2^2)` = -4 | `(-2)^2` = **4**（一元负号比幂更紧） |
| `VLOOKUP(x,t,2)` 省略第 4 参 | 精确匹配 | **近似匹配** |
| `INDEX`/`MATCH`/`VLOOKUP` 的下标 | 0 基 | **1 基** |
| `MOD(-3,2)` | -1（多数语言） | **1**（符号跟随除数） |
| 除零 | 抛出 | 返回 `#DIV/0!` |

每一条都有单元测试钉住 —— 尤其是 `-2^2`，写反了是**静默的语义改变**。

## 四、刻意与 Excel 不同的地方

逐条列出比声称"兼容 Excel"更有用：

| 项 | Excel | SheetCore | 为什么 |
|---|---|---|---|
| 文本转数字 | `"12abc"` → 12 | `#VALUE!` | Excel 的宽松规则难以预测、也难以测试 |
| 千分位 | `"1,000"` → 1000 | `#VALUE!` | 区域设置相关的解析不该进内核 |
| 近似查找遇上无序数据 | 结果不可预测 | 取最后一个 `≤` 待查值的行 | 宁可行为确定且可解释，也不要"看运气" |
| 依赖环里的下游格子 | 显示 0 | 传播 `#CYCLE!` | 更诚实：这里确实算不出来 |
| 日期 | 数字 + 格式 | 未实现 | 日期是显示层概念，内核先只做数值与文本 |

## 五、测试抓到的 bug（都是静默的那种）

记在这里，因为"哪种错最难发现"本身就是设计信息。

| bug | 后果 | 为什么难发现 |
|---|---|---|
| `last_segment` 取成"最后斜杠之前" | 子目录的文件全被静默丢弃 | 不报错，只是结果变少 |
| `A1:XFD1048576` 格子数溢出 32 位 `Int` 回绕成 0 | "区域过大就拒绝"的判断失效，静默返回空数组 | 溢出不会报错 |
| `LOG10` 被当成单元格引用（列 LOG 第 10 行） | `LOG10(2)` 解析失败 | 它**确实**是一个合法地址 |
| `SUM(A1)`（A1 为文本）返回 `#VALUE!` | 与电子表格不符 | 单测写了才会发现 |
| `shift_char` 下标多加 `-delta` | 查表越界，进程崩溃 | 这个是响的，反而最好查 |
| 注释写"后面跟 `(` 就是函数名"，代码没实现 | 与注释不符 | 注释本身不会失败 |
| 表格排版按**字符数**补空格 | 中英混排时逐列错开 | 一个汉字占 2 显示列但只占 1 字符；CLI 层没有测试，只能看截图发现 |

共同点：**除了越界那一条，全都不报错**。所以测试断言的重点不是"没崩"，
而是"结果是不是那个值"。

最后一条促成了一个结构调整：排版逻辑从 `cmd/main` 挪进 `render/` 并补了测试。
**放错层级的代码不是风格问题，是"永远不会被测到"的问题。**

### 一个只有基准测试才能发现的 bug

拓扑排序的第一版这么写：每挑一个就绪节点，就**扫一遍全部节点**找入度为 0 的，
再用一个数组做"已完成"的成员判断（线性查找）。合起来是 `O(n³)`。

- 小规模完全看不出来：100 个格子 1 ms
- 单元测试也发现不了：140 个测试全过，因为它们最多只涉及几十个格子
- 是 `bench` 在 1 万个格子上**直接跑不完**（600 秒超时）才暴露的

修法：成员判断改用 `Map`，就绪集合改用**最小堆**（既保留"取字典序最小"
的可复现性，又把每次挑选从 `O(n)` 降到 `O(log n)`），顺带发现
`recalculate` 每次都在为一个计数做整表插入排序。

同样 1000 个格子：**885 ms → 2 ms**。现在 4 万个格子全量重算 276 ms。

这个 bug 值得记下来，因为它说明了**测试通过不等于没问题** ——
单元测试保证语义正确，基准测试才能发现"正确但慢得不能用"。

## 六、尚未实现

| 项 | 状态 | 说明 |
|---|---|---|
| xlsx 等文件格式读写 | 未做 | 需要引入 ZIP + XML，与内核耦合度高，值得单独设计 |
| 日期时间类型 | 未做 | 先在数值/文本上把语义打牢 |
| 数组（动态溢出）公式 | 未做 | 需要重新设计区域在工作表里的表示 |
| 本地快照 / 持久化 | 未做 | — |

性能已有基准（`sheetcore bench`）：4 万格全量重算 276 ms，
增量重算 2000 格 13 ms。但**只有重算耗时这一项**，
没有解析吞吐、内存占用等更细的指标。

## 七、想自己看代码的话

按这个顺序读，每一步都只依赖前面：

```
value/value.mbt        值是什么、怎么互相转换
reference/reference.mbt A1 地址怎么解析、身份与回显怎么分开
formula/lexer.mbt      歧义消解：A1 / LOG10 / TRUE
formula/parser.mbt     优先级，以及为什么一元比幂紧
graph/depgraph.mbt     两个方向的边、拓扑排序、环
engine/engine.mbt      把上面串起来，产出重算轨迹
functions/builtins.mbt 函数库（聚合/数学/逻辑/文本）
functions/lookup.mbt   二维查找
cmd/main/main.mbt      CLI
```
